## 2. 新发现的遗漏（不在旧文档清单里）——更重要

### GAP-W1（最关键）：记忆回写的真实链路从没端到端验证
- 我们所有"记忆回写成功"的验证（E2/E6/三场景）都是**直接调 `_do_write`**，绕过了产品真实链路
- 产品真实链路：`enqueue()` → `flush_intents()` → `durable_jobs` 表 → **Worker `run_one()`** → 处理函数
- `api/security.py:199` 会在每个 HTTP 请求后 flush_intents，所以 job 会落表
- **但 Worker 消费端（`admin_cli.py` 的 run_one/轮询）从没在端到端测试里跑过**
- 风险：如果 Worker 没跑，用户聊完记忆不会写入 → "记得我"的产品承诺在本地运行时是断的
- 这是**产品核心闭环的最大遗漏**，比上线环节重要得多

### GAP-W2：Huey 是试点不是主力
- `USE_HUEY_TRIAL` 默认关，实际走 durable_jobs 表
- 但 `服务器与调度入口.md` 提到服务器 systemd worker 是 active——文档与当前本地状态不一致，需澄清（可能是旧部署）

### GAP-C1：危机触达闭环内存版
- `crisis_flow.py` 无持久化、`api/crisis.py` 不存在
- 危机硬门槛本身（crisis.py detect）有且验证过，但"确认轮→分级→人工复核→冷却"的闭环没持久化
- 这是 P0 安全红线，但属上线环节（需要真实人工复核流程）

### GAP-D1：AI 披露没写进 chat 响应
- ending/call 有 _DISCLOSURE 常量且验证过
- 但 `api/routes.py` 的 /api/chat 响应没有 disclosure 字段——日常陪伴的 AI 披露承诺没兑现
- 这是合规问题（拟人化陪伴），本地可修

## 5. GAP-W1 验证结果（2026-11-23，已关闭）

`eval/verify_memory_job_pipeline.py` 端到端跑通真实链路，**6 步全绿 PIPELINE_OK**：
```
✅ 用户建立(companion+consent) → enqueue → durable_jobs(pending)
→ Worker run_one(独立子进程, completed) → _do_write 落记忆(1条)
→ 召回(recalled=1)
```
回归守卫 `tests/test_memory_job_pipeline.py`（2 项）固化此链路。

**验证过程澄清的 4 个认知**（都是"看具体 case 才发现的"）：
1. 普通聊天走 Candidate 确认流、场景 extractor 才直接落 Fact——之前"回写成功"验证全是场景路径，普通聊天路径从没验
2. scope 守卫要求 companion + consent，缺失时 ScopeDenied 是**正确行为**（UC-4 隔离），不是 bug
3. 索引只在 `USE_DUAL_RECALL=1` 时建（默认开），否则落库也召回不到
4. `run_one` 的 `BEGIN IMMEDIATE` **在 try 块内**（调试中曾误判为"在 try 外、锁不走 retry"）——实际 try: 在 pos 31 < BEGIN pos 61，锁异常会被正确捕获走 retry。测试已固化正确认知。

**结论**：GAP-W1 关闭，"记得我"的真实产品链路端到端成立。剩余 GAP-D1（AI 披露写 chat 响应）、GAP-C1（危机闭环持久化，上线环节）按优先级处理。
